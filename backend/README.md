# Backend (Python / FastAPI)

API справочников и синхронизации прогресса для игры «Питомец Финни».

**Сервер не обязателен по ТЗ** — игровой цикл работает офлайн на локальном профиле.
Бэкенд нужен для двух вещей:

1. **Справочники** — каталог покупок, цели, задания, термины и правила экономики.
   Контент лежит в JSON отдельно от кода, поэтому новое задание или товар
   добавляются без пересборки приложения (ТЗ 2.5.14).
2. **Прогресс** — выгрузка и восстановление снимка локального профиля
   (переустановка приложения, смена устройства, проверка экспертом).

Персональные данные не собираются: профиль адресуется UUID, который генерирует
само приложение (ТЗ 3.5).

## Запуск локально

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate       # Windows: .venv\Scripts\activate
pip install -r requirements.txt -r requirements-dev.txt
cp .env.example .env
uvicorn app.main:app --reload
```

Открыть: http://127.0.0.1:8000/docs (Swagger UI генерируется автоматически).

База по умолчанию — файл SQLite (`finni.db`) рядом с приложением, Docker для
запуска не нужен. Для Postgres — см. Docker Compose ниже.

## Тесты и линт

```bash
pytest -v
ruff check .
```

Это же прогоняется в CI (`.github/workflows/backend-ci.yml`) на каждый push/PR,
если менялись файлы в `backend/`.

## Docker Compose (бэкенд + база данных одной командой)

Не нужно ставить Postgres руками — Compose поднимает и бэкенд, и базу в связке:

```bash
cd backend
docker compose up --build
```

Бэкенд будет на http://127.0.0.1:8000, база — на порту 5432 (логин/пароль/база:
`app`/`app`/`app`, см. `docker-compose.yml`). Остановить: `docker compose down`
(данные останутся в volume `db_data`, для полной очистки — `docker compose down -v`).

Собрать и запустить только сам бэкенд без Compose (тогда используется SQLite):

```bash
docker build -t backend .
docker run -p 8000:8000 backend
```

## Эндпоинты

Полное описание с примерами — в Swagger (`/docs`) и в `openapi.json`.

### Справочники — `GET`, без авторизации

| Путь | Что отдаёт |
|---|---|
| `/api/v1/content/manifest` | версии и ETag всех разделов — проверить, не пора ли обновиться |
| `/api/v1/content/bundle` | весь контент одним ответом (первый запуск, офлайн-кэш) |
| `/api/v1/content/catalog` | каталог покупок; фильтры `?kind=mandatory\|optional\|education`, `?category=food` |
| `/api/v1/content/catalog/{item_id}` | одна позиция |
| `/api/v1/content/goals` · `/goals/{goal_id}` | цели накопления |
| `/api/v1/content/quests` | задания; фильтры `?topic=savings`, `?tag=recovery` |
| `/api/v1/content/quests/{quest_id}` | одно задание |
| `/api/v1/content/glossary` | термины для справочного раздела; фильтр `?topic=` |
| `/api/v1/content/pets` | виды, окраски и готовые имена для онбординга |
| `/api/v1/content/economy` | доход, шаг планирования, ставка вклада, стадии питомца, обязательные правила |

**Кэширование.** Каждый раздел отдаёт `ETag` и `Cache-Control`. Мобильный
сохраняет ETag вместе с контентом и при следующем запуске присылает
`If-None-Match` — если контент не менялся, приходит `304` без тела:

```bash
curl -i http://127.0.0.1:8000/api/v1/content/goals
curl -i -H 'If-None-Match: "<etag из прошлого ответа>"' http://127.0.0.1:8000/api/v1/content/goals
```

Дешёвый способ проверить обновления разом — `/manifest`: в нём `content_version`
и ETag каждого раздела, качать нужно только изменившиеся.

### Прогресс — `/api/v1/progress/{profile_id}`

`profile_id` — UUID, который приложение генерирует само при создании профиля.

| Метод | Что делает |
|---|---|
| `PUT` | выгрузить снимок профиля целиком. `201` — сохранён впервые, `200` — обновлён |
| `GET` | забрать последний снимок (`404`, если не выгружался) |
| `DELETE` | удалить серверную копию — для раздела взрослого (ТЗ 3.5). Идемпотентно, всегда `204` |

**Разрешение конфликтов.** В снимке есть `revision` — счётчик, который клиент
увеличивает при каждой выгрузке. Если на сервере лежит бóльшая ревизия, `PUT`
вернёт `409` вместе с серверным снимком: приложение сравнивает версии и решает
само. Перезаписать принудительно — `PUT ...?force=true`. Повторная отправка той
же ревизии (клиент не получил ответ из-за сети) — не конфликт.

**Проверки на стороне сервера** — те правила ТЗ, которые нельзя нарушать:
отрицательный баланс и накопления (`422`), показатели питомца вне 0…100 (`422`),
план больше доступного бюджета (`422`). Ссылка на незнакомый сервером товар или
цель — **не** ошибка, а `warnings` в ответе: у приложения может быть более
свежий контент, и терять из-за этого прогресс нельзя.

Пример:

```bash
curl -X PUT http://127.0.0.1:8000/api/v1/progress/6f1d1b2e-8f1a-4c35-9a0e-2f2b6f7b0a11 \
  -H "Content-Type: application/json" \
  -d '{"revision":1,"updated_at":"2026-09-21T10:00:00Z","current_period":1,
       "player":{"nickname":"Ксюша"},
       "pet":{"name":"Кекс","species_id":"cat","palette_id":"mint","stage_id":"baby","xp":10,
              "stats":{"satiety":80,"happiness":70,"cleanliness":90}},
       "wallet":{"balance":35,"savings":50,"deposit":0},
       "education":{"level":1,"base_income":50,"purchased_course_ids":[]},
       "goal":{"goal_id":"goal_bike","accumulated":50}}'
```

### Служебное

`GET /health` — проверка доступности. `GET /api/v1/health` — то же плюс версия
контента. `GET /pet/{user_id}` — старая заглушка из скелета, помечена
`deprecated`, удалим, когда мобильный переедет на `/api/v1/progress`.

## Контент: где лежит и как добавить

Все справочники — JSON в `app/content/data/`:

| Файл | Что внутри | Минимум по ТЗ (раздел 2.6) |
|---|---|---|
| `catalog.json` | товары: цена, категория, влияние на питомца | 8+ позиций, по 5+ обязательных и необязательных |
| `goals.json` | цели: цена, ориентир срока, награда | 3+ цели |
| `quests.json` | задания: ситуация, варианты, объяснения | 6+ заданий по 3 темам |
| `glossary.json` | термины для справочного раздела | — |
| `pets.json` | виды, окраски, готовые имена | 9+ комбинаций внешнего вида |
| `economy.json` | доход, вклад, стадии питомца, обязательные правила | 3+ стадии, 5+ периодов демо-режима |

**Чтобы добавить задание или товар — достаточно дописать объект в JSON.** Код
трогать не нужно: количество и состав контента нигде не захардкожены.

Форма контента описана Pydantic-моделями в `app/schemas/content.py` — они же
валидируют файлы **при старте**. Если в JSON опечатка, дубль id, ссылка на
несуществующую категорию или контента стало меньше минимума из ТЗ, сервис не
поднимется и напишет, что именно не так. Так ломаный справочник не доедет до
телефона.

## Структура

```
backend/
├── app/
│   ├── main.py            # сборка приложения, lifespan, роутеры
│   ├── api/
│   │   ├── deps.py        # зависимости (доступ к загруженному контенту)
│   │   ├── http_cache.py  # ETag и Cache-Control
│   │   └── routes/        # content.py, progress.py
│   ├── content/
│   │   ├── data/          # JSON-справочники ← контент правится здесь
│   │   └── library.py     # загрузка, проверка минимума ТЗ, ETag, манифест
│   ├── core/config.py     # настройки из окружения/.env
│   ├── db/                # engine, сессии, таблица снимков профиля
│   ├── schemas/           # content.py (справочники), progress.py (прогресс)
│   └── services/progress.py  # сохранение снимка, конфликты, сверка с контентом
├── scripts/export_openapi.py # выгрузка спецификации в openapi.json
├── tests/                 # pytest: контент, прогресс, health
├── openapi.json           # спецификация OpenAPI (ТЗ 3.2) — генерируется скриптом
├── requirements.txt       # runtime-зависимости
├── requirements-dev.txt   # pytest, ruff
├── Dockerfile
├── docker-compose.yml     # бэкенд + Postgres одной командой
└── pyproject.toml         # конфиг ruff и pytest
```

## Спецификация OpenAPI

ТЗ (раздел 3.2) требует описания API в OpenAPI. Спецификация генерируется из
кода — руками её не правим:

```bash
python scripts/export_openapi.py
```

Файл `openapi.json` обновляем в том же PR, где меняется API, чтобы мобильный мог
сгенерировать клиент, не поднимая сервер.

## Как бэкенд и мобильный работают параллельно (контракт API)

1. Форма ответа описана Pydantic-моделью, FastAPI сам генерирует контракт:
   - человекочитаемо: http://127.0.0.1:8000/docs
   - машиночитаемо: http://127.0.0.1:8000/openapi.json (или файл `openapi.json` в репозитории)
2. Mobile пишет сетевой слой по этому контракту. Из эмулятора Android бэкенд на
   компьютере доступен по адресу `http://10.0.2.2:8000`.
3. Меняется форма ответа — меняем модель, контракт обновляется автоматически;
   перегенерировать `openapi.json` и написать в чат команды, что изменилось.

Важно для мобильного: **приложение должно работать и без сети.** Контент
кэшируем локально (или везём набор внутри APK), прогресс выгружаем, когда сеть
появится, — при её отсутствии показываем «нет соединения» и не теряем прогресс.
